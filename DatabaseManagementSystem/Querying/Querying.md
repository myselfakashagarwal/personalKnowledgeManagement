## Query 
A **query language** is a _formal language_ specifically designed for **retrieving, manipulating, and managing data** stored in a database or information system it’s the interface between you and structured data. A formal query is mathematically defined representation of the query of operations, its grounded in logic independent of semantics or syntax. 
## Query Processing
The query as a whole is not a physical pointer to data retrieval, its gets process by the query process component; 
### Stages in query processing 
#### Query Input Layer
The Query Input Layer is the front door of the database engine. It accepts declarative queries, usually SQL, and performs lexical analysis by tokenizing the input into keywords, identifiers, operators, and literals. It then performs syntactic analysis using a grammar, often defined in BNF or YACC style, to ensure the query conforms to SQL syntax. Semantic analysis follows, resolving object names against the system catalog, validating attribute references, checking type compatibility, privileges, and scope rules. The output is a parse tree or abstract syntax tree that structurally represents the query without execution intent. This layer is concerned with correctness, not performance.
#### Query Parser
The Query Parser transforms the AST into an internal, algebraic representation suitable for optimization. This representation is commonly relational algebra, tuple relational calculus, or a logical query tree composed of operators such as selection, projection, join, aggregation, and set operations. The parser also performs semantic normalization such as expanding views, resolving aliases, and validating grouping and aggregation rules. The result is a logical query plan that precisely defines what data is required and how it is logically related, but without specifying how it will be executed physically.
#### Query Rewrite Layer
The Query Rewrite Layer applies rule based transformations to the logical plan to improve efficiency while preserving semantics. This includes predicate pushdown, projection pushdown, constant folding, subquery unnesting, join reordering constraints, and elimination of redundant operators. For example, correlated subqueries may be rewritten as joins, and unnecessary columns may be removed early to reduce tuple width. This layer relies on equivalence rules from relational algebra and produces a semantically equivalent but often cheaper logical plan.
#### Query Optimizer
The Query Optimizer is the core cost based decision maker. It enumerates alternative logical and physical plans by exploring different join orders, join methods, access paths, and operator implementations. It uses statistics such as table cardinality, attribute histograms, data distribution, index selectivity, and correlation estimates to compute the expected cost of each plan. Cost models typically estimate I/O, CPU, and memory usage. The optimizer selects the plan with the lowest estimated cost under system constraints, often using dynamic programming or heuristic pruning to manage the search space.
#### Plan Generator
The Plan Generator converts the chosen optimized logical plan into a physical query plan. It binds each logical operator to a concrete physical operator such as sequential scan, index scan, bitmap scan, nested loop join, hash join, merge join, sort, or hash aggregation. It also determines access paths, index usage, join algorithms, and operator ordering. The output is an executable operator tree or directed acyclic graph annotated with physical properties like expected cardinality, required memory, and execution order.
#### Execution Engine
The Execution Engine is responsible for running the physical plan. It implements execution models such as iterator based pull execution, push based pipelining, or vectorized execution. Operators request or emit tuples according to this model, managing intermediate results without materializing them unless required. The engine handles runtime concerns including memory allocation, temporary file creation, spilling to disk, concurrency control hooks, and error handling. It drives the plan until all result tuples are produced.
#### Access Methods Layer
The Access Methods Layer abstracts how records are retrieved from storage. It implements low level operations such as table scans, index lookups, range scans, and record fetches. This layer decides how to traverse data structures like B trees, hash indexes, or heap files and exposes a uniform interface to higher layers. Its primary responsibility is efficient record level access while hiding storage layout complexity from the execution engine.
#### Buffer Manager
The Buffer Manager manages the database buffer pool in main memory. It loads disk pages into memory on demand, pins pages while they are in use, and evicts pages using replacement policies such as LRU, CLOCK, or adaptive variants. It ensures consistency by coordinating with logging and recovery mechanisms and minimizes disk I/O by caching frequently accessed pages. Effective buffer management is critical for query performance because disk I/O dominates cost.
#### Storage Manager
The Storage Manager controls the physical layout of data on disk. It manages files, extents, pages, and blocks, handles space allocation and deallocation, and maintains metadata about storage structures. It interfaces directly with the operating system for I/O operations and ensures durability through write ordering and integration with the log manager. This layer defines how tuples are physically stored and retrieved at the block level.
#### Query Result Construction
The Query Result Construction phase assembles the final output produced by the execution engine. It applies any remaining formatting, ordering, projection, or aggregation required by the query specification. Results are converted into a client consumable format such as rows, cursors, or serialized data streams. This layer is responsible for delivering the completed result set to the application or front end with correct schema and data types.
#### Example Query Flow
In the example query SELECT name FROM Employees WHERE dept_id = 10, the SQL text enters the input layer for validation, is parsed into a logical plan consisting of a selection on dept_id followed by a projection on name, rewritten to push the predicate as close to the table scan as possible, optimized to choose an index scan if an index exists on dept_id, converted into a physical plan using that index, executed by fetching qualifying tuples through the access methods and buffer manager from storage, and finally formatted into a result set containing only the name column.
